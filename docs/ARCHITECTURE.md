# 知底 KnowBase · 项目详解

> 本文面向两类读者:想快速理解"这个项目解决什么问题、怎么解决"的评审者与使用者,以及要二次开发的工程师。
> 所有结论都能在源码与测试中找到对应实现。

## 1. 要解决的问题

企业里 HR、IT、财务每天回答大量重复问题("年假怎么算""VPN 连不上"),答案散落在制度文档里;
直接把文档丢给大模型又会带来三个企业级风险:

| 风险 | 后果 | 知底的对策 |
|---|---|---|
| 模型编造 | 员工按错误答案办事 | 严格依据资料作答 + `[n]` 出处引用 + 资料不足就拒答并转人工 |
| 越权泄露 | 低权限员工问出薪酬、预算等机密 | 部门权限标签在检索层强制过滤,取回正文时二次校验 |
| 不可运营 | 不知道哪些问题答不出、哪些答得差 | 拒答与点踩沉淀为"知识缺口",可导出 CSV 排期补文档 |

## 2. 一次问答经历了什么

```
员工提问
  │ ① 入口脱敏(手机号/身份证/银行卡/邮箱)      ← 之后的一切只看到脱敏文本
  │ ② 寒暄规则                                   命中即回,零成本
  │ ③ FAQ(自研 BM25,按部门权限过滤)             命中即回,答案由运营掌控
  │ ④ 追问改写("那病假呢" → "病假需要什么证明")   仅多轮追问时触发
  │ ⑤ 检索策略:直接 / 假设问题 / 子查询 / 回溯    白名单校验,短问题省一次 LLM
  │ ⑥ 混合检索(稠密+稀疏),检索前强制权限过滤
  │ ⑦ 取父块(关系库二次校验权限与文档状态)
  │ ⑧ 重排 → 相关度阈值(低于阈值 = 知识库里没有)
  ├─ 无可靠资料 → 拒答 + 人工渠道(route=refused,计入知识缺口)
  └─ 有资料 → ⑨ LLM 严格依据资料生成,标注 [n] → 引用来源(文档·章节·页码·版本)
  ▼
落库留痕(问答轮次、引用、耗时、模型、请求 ID),指标计数
```

**成本由低到高、命中即返回**是这条链路的核心:寒暄和 FAQ 不调用任何模型,大部分高频问题在毫秒级结束。

## 3. 模块职责

| 目录 | 职责 | 关键文件 |
|---|---|---|
| `api/` | 协议层:路由、鉴权依赖、参数校验、SSE/WebSocket | `chat.py` `admin.py` `deps.py` |
| `services/` | 业务编排:问答流程、FAQ 匹配、审计 | `chat_service.py` `faq_service.py` |
| `rag/` | 检索与生成能力 | `retrieval_service.py` `retrievers.py` `rewriter.py` `intent.py` `bm25.py` |
| `rag/ingestion/` | 入库:加载 → 父子块 → 去重/版本 → 索引 | `pipeline.py` `loaders.py` `chunking.py` |
| `db/` `cache/` | 关系库模型与会话;KV(Redis/内存) | `models.py` `kv.py` |
| `core/` | 配置、日志、安全、脱敏、指标 | `config.py` `security.py` `pii.py` `metrics.py` |
| `container.py` | 组合根:唯一创建各组件的地方 | |

分层约定:`api → services → rag/db/cache → core`,下层不依赖上层;组件之间只依赖协议(`LLM` / `Retriever` / `Reranker` / `KV`),
所以测试里可以直接注入假实现,不需要 GPU、向量库或真实模型。

## 4. 关键设计决策

**4.1 为什么先 FAQ 后 RAG。** 高频问题答案稳定,走检索+生成既慢又贵还可能答偏。FAQ 层用自研 BM25,置信度归一化到 0~1
(得分 ÷ "完全匹配时的理想得分"),阈值与语料规模无关;并要求第一名领先第二名至少 `faq_margin`,避免相近问题互相抢答。

**4.2 为什么拒答是一等公民。** 检索相关度低于 `min_relevance` 时不带空上下文去调用 LLM(那样模型一定会编),
直接拒答并给出人工渠道。模型自己判断资料不足(固定话术"知识库中暂无相关信息")同样记为 `refused`。

**4.3 权限为什么做两道。** 第一道在向量库/内存索引的过滤表达式里按 `acl_tags` 过滤;第二道在取父块时按关系库中文档的
ACL 与状态再校验。即使向量库数据滞后(刚改权限/刚下线),也不会泄露。标签来自服务端签发的令牌并经白名单正则校验,
不拼接任何用户输入。

**4.4 父子块。** 小块(约 300 字)参与检索,命中准;大块(约 1200 字)送给 LLM,上下文完整。先按文档章节切分,
每个父块只属于一个章节,引用才能精确到「文档 · 章节 · 页码」。

**4.5 文档版本与切换。** 同标题再上传即 `version+1`;新版本入库成功后才归档旧版本,切换期间旧版本继续服务。
失败则新文档标记 `failed` 并清理半成品。内容哈希相同视为重复,仅在权限/分类变化时重建索引。

**4.6 追问改写只作用于检索。** 改写结果不替代用户原问题展示或落库;LLM 输出会校验长度与换行,
失败时退化为"上一问 + 本问"拼接,保证不会因为改写失败而问答失败。

**4.7 脱敏在入口。** 问题进入系统的第一步就脱敏,检索、LLM、落库、日志看到的都是脱敏文本。
银行卡需通过 Luhn 校验才替换,宁可漏掉也不误伤工号、金额、制度编号。

**4.8 流式期间不占数据库连接。** 问答分"读历史/FAQ"和"落库"两个短事务,LLM 流式生成在两者之间,
慢模型不会耗尽连接池。

**4.9 Redis 故障时放行。** 限流与令牌吊销是辅助防线,Redis 抖动不应让全员无法登录,故 fail-open 并告警。

## 5. 数据模型

`Department` / `User` → `ChatSession` → `ChatTurn`(含路由、引用、耗时、模型、请求 ID)→ `Feedback`;
`Document`(版本、校验和、ACL、状态)→ `DocParent`(父块正文);`FaqEntry`;`AuditLog`。
`ChatTurn.route` ∈ `chitchat | faq | rag | refused | general | error`,运营统计与知识缺口都基于它。

## 6. 权限与安全清单

- 登录:PBKDF2-SHA256 密码哈希;用户不存在时也做一次假校验以抹平耗时;5 分钟 10 次失败锁定;
- 令牌:HS256 JWT,带 `jti`,登出写吊销名单;每次请求以数据库为准复核账号状态,停用即时生效;
- 角色:`employee` < `kb_admin` < `admin`;越权访问记审计 `authz.denied`;
- 输入:长度上限、分类/部门/标签白名单正则;CSV 导出做公式注入防护;
- 生产:`KNOWBASE_ENV=prod` 强校验密钥长度、非 SQLite、非内存检索、必须配置 LLM;关闭 `/docs`;`/metrics` 需令牌;
- 提示词:资料与历史声明为"数据而非指令",降低注入风险。

## 7. 可观测性

- 请求 ID 贯穿日志与响应头 `X-Request-ID`;可选 JSON 日志;
- `/metrics`(Prometheus 文本):HTTP 请求数/耗时(按路由模板)、问答数/耗时(按路由)、脱敏命中数;
- `/health/live`、`/health/ready` 对接 K8s 探针;
- 审计日志与问答留痕均可按请求 ID 关联。

## 8. 质量保障

- `pytest`(51 个用例):鉴权、权限隔离、FAQ 置信度、版本切换、入库回退、SSE/WebSocket、限流、审计、脱敏、追问改写、指标、导出;
- 评估门禁 `scripts/evaluate_rag.py`:hit@1 / hit@3、**权限泄露数必须为 0**、拒答准确率;不达标退出码为 1,已接入 CI;
- CI:ruff、pytest、评估门禁、gitleaks 密钥扫描。

## 9. 扩展点

| 想做的事 | 改哪里 |
|---|---|
| 接入企业微信/钉钉/飞书/OIDC | 新增 `/auth/sso/callback`,校验第三方身份后签发同样的 JWT,权限逻辑不变 |
| 支持扫描件/PPT/图片 | `register_loader(".pptx", fn)` |
| 更换向量库 | 实现 `Retriever` 协议并在 `container.py` 选择 |
| 更换/新增模型供应商 | 实现 `LLM` 协议 |
| 大批量/高可靠入库 | 把 `IngestionService.ingest` 放进任务队列 |
| 版本化迁移 | 引入 Alembic,替换启动时自动建表 |

## 10. 已知边界(上线前必读)

1. **Milvus 检索器、重排器与 `docker-compose.yml` 未在真实环境验证**,自动化测试覆盖除向量库与模型之外的全部逻辑;
2. 入库默认用进程内后台任务,重启会中断进行中的任务(可 `/reindex` 重跑);
3. 脱敏只覆盖结构化号码,不识别姓名、地址等自由文本;
4. 问答内容会发送给所配置的 LLM,涉密场景请使用私有化模型;
5. 示例数据均为虚构;接入真实制度后须补充黄金集并重新标定 `KNOWBASE_MIN_RELEVANCE`;
6. 仓库未指定 License,请按公司政策补充。
